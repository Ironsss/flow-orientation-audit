# A1 — BoT-IoT dependence sensitivity: report (2026-09-27)

## Question

`results/dependence/cluster_bootstrap_botiot.csv` (host-pair cluster bootstrap,
already computed before this audit) showed 5 of 8 verifiable BoT-IoT attack
groups losing confident directional-asymmetry orientation, leaving only
DDoS/TCP, DDoS/UDP, DoS/UDP confidently oriented. This audit asks whether that
3-of-8 pattern is an artifact of the specific dependence unit chosen
(host-pair) or a robust finding, by adding two more resampling methods
(time-block, two-stage host-pair-then-flow) and a cluster-weighted point
estimate.

## Threat to validity

Treating 73M BoT-IoT flows as independent resampling units when they are
generated by a handful of machines over a short capture window can produce
false precision. The host-pair bootstrap already tests this; this audit
checks whether time-block and two-stage (pair-then-flow) resampling tell the
same story.

## Method

1. **Inventory extension** (`scripts/dependence_cluster_inventory.py`): added
   `n_dst_hosts`, and for BoT-IoT, `n_attacker_hosts` and
   `n_time_blocks_{60s,300s,600s}`. Rerun against real data; rewrote
   `results/dependence/cluster_inventory_botiot.csv` (diagnostic, not
   confirmatory — this is the one file the plan explicitly permits rewriting).
2. **Method D — time-block bootstrap** (`scripts/audit_a1_bot_dependence.py`):
   cluster id = `timestamp // block_seconds`, for 60s, 300s and 600s (freeze
   item 2). Same `MIN_CLUSTERS = 10` gate as the host-pair bootstrap
   (imported from `scripts/dependence_cluster_bootstrap.py`), applied
   separately at each granularity. A group with fewer than 10 blocks at a
   granularity is reported "not computed" there, not silently skipped. The
   first run computed 300s only. 60s and 600s were added in a second run
   (see "Completion of the freeze" below).
3. **Method C — two-stage bootstrap**: host-pairs resampled with replacement,
   then flows resampled within each drawn pair-replicate via the multinomial-
   additivity shortcut (a pair drawn `m` times contributes one
   `Multinomial(m * n_pair, uniform)` weight draw over its own rows, which is
   distributionally identical to `m` independent `Multinomial(n_pair, uniform)`
   draws — verified against the literal per-draw definition in
   `tests/test_audit_a1_bot_dependence.py::test_two_stage_bootstrap_reduces_to_flow_bootstrap_for_one_row_per_pair`).
4. **Cluster-weighted point estimate**: point `auc_signed` recomputed with
   each host-pair weighted `1 / n_pair_rows`.
5. Assembled `results/audit/a1_bot_dependence/comparison.csv`, one row per
   verifiable group (host-pairs $\geq$ 10), joining the existing host-pair
   result with the two new methods and `sign_stable` (bool: confident and
   same-side across flow, host-pair, two-stage, and 300s time-block when
   available; see Limitations for how this relates to the freeze's
   "all computed methods").
6. **Benign-concentration diagnostic** (POST-HOC, added after all of the
   above): `scripts/audit_a1_benign_concentration.py` measures host-pair
   concentration of the benign reference and runs side-isolated
   bootstraps. See "Why host-pair and time-block disagree" in Results.

`B = 2000` bootstrap draws, `SEED = 20260922`, both imported unchanged from
`scripts/run_unsw_external_validation.py` via the same `importlib` re-import
pattern `scripts/dependence_cluster_bootstrap.py` already uses.

### Bugs found in the brief's code and fixed

- **`_inventory_rows`'s `n_attacker_hosts` expression used `pl.element()`
  outside a `list.eval` context**, which polars rejects
  (`InvalidOperationError: 'element' is not allowed in this context`).
  Fixed by exploding the `[src_ip, dst_ip]` list into its own column first,
  then filtering and counting distinct values on that column directly —
  same result, valid polars. Verified on synthetic data before running
  against the full dataset.
- **`stable()`'s `same_side` check was a no-op bug**:
  `len({r["flow_auc_signed"] > 0.5 for _ in cis}) == 1` iterates over `cis`
  but evaluates the same constant boolean each time, so the resulting set
  always has exactly one element — `same_side` was `True` unconditionally,
  regardless of what the actual CIs said. Replaced with a check that derives
  each CI's own side (`lo > 0.5` positive, `hi < 0.5` negative, `None` if it
  straddles 0.5 i.e. not confident) and requires every computed CI to be
  confident *and* agree on the side. This is a correctness fix, not a change
  of statistical method — the intended semantics ("same orientation and
  confident across all computed methods") were already stated in
  `A1_BOT_DEPENDENCE.md` item 5; the original code just didn't implement it.

Both fixes are transcription/implementation bugs in code that had not been
executed before this task, not changes to the frozen analysis design.

and writes `results/audit/a1_bot_dependence/benign_concentration.csv`.

unchanged. Each side-isolated bootstrap uses its own
`np.random.default_rng(SEED)` per group.

**What this means for the count.** Host-pair is the unit that can see the
dominant source of uncertainty here: which benign host-pairs make up the
reference. Time-block cannot, by construction. The count of confidently
oriented verifiable groups is therefore **3 of 8** (DDoS/TCP, DDoS/UDP,
DoS/UDP). The other five are not confidently oriented. For four of them
the orientation depends on whether one benign host-pair is in the
reference, and in what proportion.

This is the same phenomenon A2 found by a different route (the final
whole-branch review's I3 item). A2 showed that the negative orientations
are set by the benign reference, which is unusually source-dominated
(median `A_bytes` +4.49, `docs/ESTADO-ACTUAL.md`) and only 47.3% answered.
The dominant pair (median +5.18, 25% of rows) is a large part of that
skew. A2 changes the reference by
conditioning on reply presence. The cluster-weighted point changes it by
weighting pairs equally. Host-pair resampling changes it at random. All
three move the negative groups toward or past 0.5.

## Impact on manuscript claims

Per `A1_BOT_DEPENDENCE.md`'s frozen interpretation, **bucket 2 applies**
("a different subset survives under time-block or two-stage -> the
dependence unit matters; report which unit and widen the claim's caveats
accordingly. Do not pick whichever unit looks best"), **not bucket 1**.
Completing the freeze (60s/600s) confirms this classification and makes it
sharper. It does not change it. Under time-block (60s, the only
granularity computable for all 8), **all 8** verifiable groups keep a
confident orientation on the flow-level side. Under host-pair, 3 do. The
confident subset is therefore different under the two units, which is
bucket 2's condition. Two-stage matches host-pair, but at BoT-IoT's scale
it is not an independent check (see Results).

Where the units agree and where they do not:

- **DDoS/TCP, DDoS/UDP, DoS/UDP: all computed methods agree** (flow,
  host-pair, two-stage, 60s time-block, all confidently positive). The
  first run could not say this, because 300s was not computable for them.
  Their orientation is not an artifact of choosing host-pair.
- **Recon/Service scan, Recon/OS fingerprint, DDoS/HTTP, DoS/TCP, DoS/HTTP:
  methods disagree, and the disagreement is explained.** Time-block (every
  granularity computed) agrees with flow. Host-pair and two-stage are not
  confident. The benign-concentration diagnostic (Results) shows why:
  host-pair's width comes almost entirely from resampling the benign
  host-pairs, and for four of these groups one benign pair (25.2% of the
  reference) sits above essentially every attack row. Time-block keeps that
  pair's share near 25% in every replicate (SD 0.019 vs. 0.182 under
  host-pair), so it cannot see this uncertainty.

Bucket 2's instruction is "do not pick whichever unit looks best." The
general principle stands: a unit is not chosen because its answer is
favourable. Here the choice is made on a measured property, not on the
answer. Host-pair captures the dominant source of uncertainty (which
benign host-pairs make up the reference). Time-block, by construction,
does not. Host-pair is also the less favourable of the two. **The count of
confidently oriented verifiable groups is 3 of 8** (DDoS/TCP, DDoS/UDP,
DoS/UDP). It is not "3 to 8 depending on the dependence structure," as an
earlier version of this report said. Time-block's confidence on the other
five is not an alternative valid reading. It is the output of a resampling
unit that holds the relevant source of variation fixed.

For the manuscript: this matches the statement its Limitations already
make ("only 3 of 8 checkable groups keep a confident orientation"), so the
count needs no change. What changes is the reason. The five groups lose
confidence mainly because their orientation depends on the composition of
the benign reference, not because 32 attack-side pairs are too few.
DoS/TCP is a marginal case (see Results).

This is POST-HOC robustness analysis; it does not reopen the confirmatory
verdict. It is **not independent** of A2's finding that the negative
orientations reverse once reply presence is controlled. Both come from the
same property: BoT-IoT's benign reference is small, source-dominated
(median `A_bytes` +4.49) and concentrated in a few host-pairs, one of which
holds a quarter of it. A2 changes that reference by reply presence, the
cluster-weighted point by pair weighting, and host-pair resampling at
random. All three move the negative groups toward or past 0.5. Time-block
confirms only that the *flow-weighted* orientation is not a
temporal-dependence artifact.

One additional, honest observation that goes beyond the pre-registered
`sign_stable` gate (and is reported here because it is directly relevant,
not because it changes the classification): the **cluster-weighted point
estimate** flips sign relative to the original row-weighted `flow_auc_signed`
for all four groups whose flow-level orientation was "negative"
(Recon/Service scan, Recon/OS fingerprint, DDoS/HTTP, DoS/HTTP) — each moves
from a flow-level AUC below 0.5 to a cluster-weighted point above 0.8. For
the four groups whose flow-level orientation was "positive," the
cluster-weighted point stays positive and becomes more extreme. This is
consistent with a small number of host-pairs (as few as 32, sometimes with
very unequal row counts — the per-pair row count varies by three orders of
magnitude within a group, see `rows_per_pair_median` in the inventory)
dominating the row-weighted point estimate in one direction while being
equally weighted in the other. This is not part of the pre-registered
`sign_stable` criterion (which is CI-based) and does not change the A1
classification above, but it is a second, independent illustration of the
same underlying threat to validity the audit's question names: BoT-IoT's
low host-pair count concentrates a great deal of leverage in how those pairs
are weighted. On the benign side that leverage is now measured: one pair
holds 25.2% of the reference (Results), and equal weighting cuts it to
1/347. Its consequence for the manuscript's sign-heterogeneity claim
is substantial: with pairs weighted equally, all 8 verifiable groups are
positive (0.785-0.934), so no negative orientation remains among them.
`AUDIT_SYNTHESIS.md` combines this with A2's answered-only result; that
combination is the main synthesis-level finding of Phase I.

## Limitations

- **Freeze now complete: 60s, 300s and 600s time blocks have all been
  run.** History: `A1_BOT_DEPENDENCE.md` item 2 froze
  `block_seconds` in `{60, 300, 600}`, but the first run implemented 300s
  only. The freeze's own item-5 column list names only
  `timeblock_300s_ci_{lo,hi}`, and the implementation followed that list.
  A whole-branch review flagged the gap. A second run added 60s and 600s
  without changing any other part of the method, and all previously
  committed values were verified bit-identical (see "Completion of the
  freeze" in Results). The disclosed deviation is closed. What stays
  **POST-HOC** is that the 60s/600s numbers were computed after the 300s,
  host-pair and two-stage results were already known. The method and gate
  were frozen in advance. The timing of their execution was not.
- **Both cluster units rest on few clusters on the attack side.** At 60s
  the flood groups have 21-43 attack-side time blocks. Host-pair has 32
  attack-side pairs for every verifiable group. Both are above
  `MIN_CLUSTERS` (10) but not many, and percentile bootstrap CIs from that
  few clusters can under-cover, under **either** method. No further
  time-block granularity is computable for the floods (3-9 blocks at 300s
  and 600s). The small cluster count does **not** explain the gap between
  the methods: host-pair CIs are 3.9-6.5 times wider than 60s time-block
  CIs with a comparable number of attack-side clusters. The gap comes from
  what each unit can vary on the benign side (benign-concentration
  diagnostic, Results), and attack-only pair resampling keeps all 8 groups
  confident.
- `sign_stable` is not computed exactly as the freeze words it. Freeze
  item 5 defines it as confident and same-side "across all computed
  methods", which literally includes the 60s/600s time-block columns once
  they exist. The implemented column uses the methods available in the
  first run: flow, host-pair, two-stage, and 300s where computable.
  **Verified:** recomputing it with 60s and 600s included gives the same
  value for all 8 groups (the 3 `true` rows are confidently positive at
  60s, and the 5 `false` rows are already false because of host-pair). The
  committed column was left unchanged.
- The two-stage bootstrap's per-pair `rng.multinomial` calls dominate the
  wall-clock cost for the four large flood groups (roughly 90 minutes total
  for this run); this is a real computational limitation of the method at
  BoT-IoT's scale, not evidence against the result.
- `sign_stable` is a binary summary that hides *why* a row is false: for
  Recon/Service scan and Recon/OS fingerprint it is false because
  host-pair/two-stage straddle 0.5 while time-block is confidently
  negative, not because every method is non-confident. The same holds at
  60s for DDoS/HTTP, DoS/TCP and DoS/HTTP. The benign-concentration
  diagnostic explains that split. The underlying numbers in
  `comparison.csv` and `benign_concentration.csv` should be consulted
  directly for any claim finer-grained than `sign_stable`.
- The benign-concentration diagnostic is itself POST-HOC. It was written
  after a reviewer's uncommitted check suggested the mechanism, and after
  all A1 results were known. It explains the existing CIs. It does not
  change any of them.
