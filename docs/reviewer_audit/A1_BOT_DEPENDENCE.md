# A1 — BoT-IoT dependence sensitivity (frozen 2026-09-27)

## Question

`results/dependence/cluster_bootstrap_botiot.csv` (already computed) shows
5 of 8 verifiable BoT-IoT groups lose confident orientation under
host-pair cluster bootstrap (Recon/Service scan, Recon/OS fingerprint,
DDoS/HTTP, DoS/TCP, DoS/HTTP all flip to "near-neutral or not confident");
only DDoS/TCP, DDoS/UDP, DoS/UDP survive. This audit asks whether that
finding is an artifact of the specific dependence unit chosen (host-pair)
by testing two more units.

## Threat to validity

Treating 73M BoT-IoT flows as independent resampling units when they are
generated by a handful of machines over a short capture window can produce
false precision. The host-pair bootstrap already tests this; A1 checks
whether time-block and two-stage (pair-then-flow) resampling tell the same
story.

## What this does NOT touch

`results/botiot/verdict.json`'s `STRONG REPLICATION` string,
`results/botiot/asymmetry_by_attack.csv`, `results/dependence/cluster_bootstrap_botiot.csv`.
This audit reads those files, never writes them.

## Reproducibility check (no new code — cites existing evidence)

`scripts/run_botiot_h3.py`'s `sklearn_check()` (line 229) already asserts,
on every run, that the counting-AUC engine's `auc_signed` for `A_bytes`
matches `sklearn.metrics.roc_auc_score` on the same rows, for all ten
groups — this is the bit-for-bit independent-implementation check A1.1
asks for, and it already passed on the confirmatory run (BOTIOT_H3_FINDINGS.md).
A1 does not re-implement this; the report cites it.

## New analysis (frozen before execution)

1. Extend `scripts/dependence_cluster_inventory.py`'s BoT-IoT rows with
   `n_dst_hosts`, `n_attacker_hosts`, `n_time_blocks_60s`, `n_time_blocks_300s`,
   `n_time_blocks_600s`.
2. **Method D — time-block bootstrap**: cluster id = `timestamp // block_seconds`,
   for `block_seconds` in `{60, 300, 600}`. Same `MIN_CLUSTERS = 10` gate as
   the host-pair bootstrap; a group with fewer than 10 blocks at a given
   granularity is "not computed" at that granularity, not silently skipped.
3. **Method C — two-stage bootstrap**: host-pairs resampled with replacement,
   then flows resampled within each drawn pair-replicate. A pair drawn `m`
   times contributes a `Multinomial(m * n_pair, uniform)` weight vector over
   its own rows (multinomial additivity over independent equal-probability
   trials).
4. **Cluster-weighted point estimate**: recompute the point `auc_signed` with
   each host-pair weighted `1 / n_pair_rows`, so no single dominant pair (e.g.
   a UDP-flood pair with millions of rows) sets the point estimate.
5. Assemble `results/audit/a1_bot_dependence/comparison.csv`: one row per
   group, columns `flow_auc_signed`, `flow_ci_{lo,hi}`, `hostpair_ci_{lo,hi}`
   (from the existing `results/dependence/cluster_bootstrap_botiot.csv`),
   `timeblock_300s_ci_{lo,hi}`, `two_stage_ci_{lo,hi}`, `cluster_weighted_point`,
   `sign_stable` (bool: same orientation and still confident across all
   computed methods).

## Frozen interpretation

- **All methods keep the same 3-of-8 pattern** (DDoS/TCP, DDoS/UDP, DoS/UDP
  survive; the other 5 verifiable groups don't) -> BoT-IoT's dependence
  sensitivity is a robust finding, not a host-pair artifact. Manuscript
  language stays as already written in Limitations.
- **A different subset survives under time-block or two-stage** -> the
  dependence unit matters; report which unit and widen the claim's caveats
  accordingly. Do not pick whichever unit looks best.
- **All methods lose all 8** -> the host-pair result may have been
  optimistic; strengthen the caveat further.
